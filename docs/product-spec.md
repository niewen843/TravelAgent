# 旅游规划智能体产品规格

版本：v0.5（讨论稿）  
日期：2026-09-30

本文用于讨论产品行为与范围。已确认的规则包括国内单城市自由行、交通和住宿信息接入、预算默认按人均、出行日期必须确认、冲突由用户决定、前端选项交互、指定酒店费用口径确认、天气通过 MCP 查询，以及查询失败主动说明。电脑端采用聊天旁的行程面板，手机端采用“聊天／行程”全屏切换，安排修改通过自然语言交给智能体。已有行程的天气更新由用户点击打开当前行程触发。

## 1. 产品目标

用户从一句不完整的旅行意向开始，通过少量对话获得一份可执行、可解释、可持续调整的行程；出发前和旅途中都可以继续修改。

智能体应帮助用户回答：

- 我还需要决定什么，才能开始规划？
- 每天去哪里，先后顺序是什么，怎么移动？
- 这样的安排是否符合时间、预算、兴趣和体力？
- 哪些事项需要提前预约或进一步确认？
- 如果迟到、下雨、疲惫或改变想法，剩余行程怎么调整？

产品成功的表现：用户不必重新解释已知信息，也不必自己检查每次修改带来的时间和路线冲突。

## 2. 首版范围

首版以国内单城市自由行为目标，覆盖出发前规划和旅途中调整。交通信息包含往返目的地的高铁票等城际交通，以及城市内公共交通；酒店建议结合用户偏好、房型需求与行程安排生成。查询和推荐属于首版范围，自动预订尚未确定。

| 能力 | 首版要求 |
| --- | --- |
| 自然语言需求收集 | 支持信息不完整的输入、跨轮补充、纠正和改主意 |
| 初版生成 | 输出每日路线、预计时长、交通建议、预算区间和待办事项 |
| 交通查询 | 通过第三方 API/MCP 获取高铁票等交通信息及公共交通路线，检查与行程的衔接 |
| 酒店推荐 | 通过 MCP 获取酒店信息，结合日期、偏好、人数、房型、预算与行程位置推荐 |
| 景点查询 | 通过 MCP 获取景点信息，支持地点、开放、预约和费用核实 |
| 天气与准备 | 通过 MCP 根据确认的日期查询当地天气，给出衣物、雨具等携带建议 |
| 选项交互 | 候选、是非确认和冲突解决方案由前端提供可点击选项，点击反馈进入后续规划 |
| 行程修改 | 支持偏好调整、项目增删移动、时间变化和现场变化 |
| 事实核实 | 对支撑可执行性的地点、营业、预约和路线信息提供核实状态 |
| 行程保存 | 能重新打开会话并继续规划，保留最新版本和修改记录 |
| 旅途中使用 | 用户可主动提供位置、时间和完成情况，无需依赖持续定位 |

跨城市长线、自动购票及酒店下单、多人协同编辑和主动推送暂作为后续能力。票价、余票、酒店价格及房态等查询按第三方工具实际提供的能力展示；未返回的数据不能补写为已查询结果。具体 API/MCP 服务在技术方案阶段确定。

## 3. 用户与核心场景

目标用户是需要帮助组织自由行的人，包括尚未确定需求的人、已经有部分安排的人，以及在旅途中需要重新安排的人。

核心场景：

1. **模糊意向**：“我想去武汉玩几天。”智能体逐步澄清需求。
2. **信息较完整**：“去武汉 3 天，两个人，喜欢美食和历史。”智能体补齐影响可执行性的信息，生成初版。
3. **出发前修改**：“第二天太赶了，少走一点。”智能体减少负担并检查其他天的安排。
4. **旅途中调整**：“今天下午 3 点才到酒店，原来的安排来不及了。”智能体基于剩余时间重排。
5. **保留固定安排**：“明天下午 2 点已经有预约，其他都能改。”智能体围绕固定安排规划。
6. **继续已有行程**：“上次那个武汉计划，把最后一天改成购物。”智能体恢复上下文并修改对应行程。

## 4. 信息收集与追问

### 4.1 信息项

| 信息 | 对规划的影响 | 收集策略 |
| --- | --- | --- |
| 目的地 | 决定规划范围 | 生成目的地行程前需要明确 |
| 天数或日期区间 | 决定可用天数 | 需要明确；“玩几天”不视为已给出天数 |
| 出行日期 | 影响天气、开放、预约、票价和酒店信息 | 核心条件，必须向用户确认具体日期，不允许假设 |
| 出发地、抵达与离开时间 | 决定交通查询条件与首末日可用时间 | 查询往返交通前确认出发地；未订交通时可用查询结果向用户建议抵离方案 |
| 同行者 | 影响节奏、活动适合度和预算 | 优先询问；不自动假定儿童或老人有特定限制 |
| 预算 | 影响酒店、餐饮、交通和付费活动 | 核心条件，明确金额与覆盖范围；默认人均，用户指定全体或其他口径时遵从用户要求 |
| 兴趣、必去和避雷项目 | 决定推荐内容 | 优先获取主要兴趣，其余逐步补充 |
| 节奏和行动限制 | 影响步行、休息和活动密度 | 可给简单选项；明确限制时作为约束 |
| 住宿偏好与房型 | 影响酒店筛选和费用 | 询问价格、区域、设施及单人间、双人间等需求；有歧义时确认房间数量、入住人数和床型 |
| 住宿区域、已订项目 | 影响起终点和固定时段 | 已知则直接使用；未订酒店时结合行程提供候选，不当作已确定住宿 |

### 4.2 追问规则

- 从每轮输入中提取所有相关信息，不重复询问已明确的信息。
- 第一轮通常询问 2～3 个最影响当前规划的问题，避免一次展示完整问卷。
- 根据已知信息动态决定下一轮问题，不采用固定问答顺序。
- 明显冲突需要澄清，例如“总共 3 天”与“周一到周五”不一致。
- 区分“不知道”“没有偏好”和“尚未回答”。用户明确不知道的信息，不反复追问。
- 日期未定时，可以继续收集需求或帮助用户比较日期选择，但必须取得用户确认后才能生成初版行程。
- 预算金额或覆盖范围不明确时需要追问，不默认金额；未指定计算口径时按人均，并在需求摘要中展示。
- 用户更正信息时更新当前需求；若影响现有行程，说明需要调整的部分。
- 对目的地、天数、日期、人数、预算和已订项目等信息，不静默采用会明显改变方案的假设。
- 用户要求先看草案时，缺失的非关键信息可采用明确、可修改的假设。
- 日期和预算属于核心信息，不因用户要求先看草案而自动补齐。对需求或规划冲突，展示问题和可选方案，按照用户确认的方案执行。
- 候选选择、是非确认和可枚举的问题通过前端选项收集反馈，用户无需重新输入选项内容；同时支持用户主动用自然语言表达决定。
- 用户直接指定酒店时，若住宿费用口径尚未明确，应询问“酒店费用是否在旅行预算之外单独计算？”，提供“单独计算”和“计入预算”选项。用户已明确口径时直接记录，不重复询问。

### 4.3 何时开始生成

**可以生成草案：**目的地、具体出行日期、天数、人数和预算金额及覆盖范围已明确，且不存在尚未解决的需求冲突。日期区间可用于计算天数，无需重复追问；一般兴趣或设施偏好等非核心缺口可以明确标注。涉及交通或酒店建议时，还需满足对应查询的必要条件。

**可以生成较完整的计划：**在草案条件基础上，每日可用时间、主要偏好和固定安排已明确，交通、酒店、景点及天气等必要查询已完成，或查询缺口已向用户说明且不会阻断核心路线。

**需要继续追问：**目的地、日期、天数、人数或预算不明确，需求互相矛盾，或者某个缺口决定方案能否成立。

用户直接要求生成时，应根据已有信息给出能成立的结果；仍缺少核心条件时，只追问必要条件。系统不得把信息齐全等同于事实已核实。

## 5. 初版行程要求

### 5.1 展示内容

一份行程包括：

1. **需求摘要**：日期、人数、预算口径、兴趣、节奏和固定安排。
2. **规划假设与待确认项**：例如首日到达时间、住宿区域、未核实的营业信息。
3. **每日概览**：主题、主要区域、活动密度和预计花费。
4. **每日明细**：活动顺序、建议时间段、预计游玩时长、移动方式和移动时间。
5. **预约与准备清单**：需要预约、携带或提前核实的事项。
6. **必要的替代方案**：对天气敏感或存在明显不确定性的安排提供备选。
7. **交通候选**：高铁等往返交通和市内公共交通建议，展示工具实际返回的班次、时间、价格及查询时间。
8. **酒店候选**：推荐原因、位置、房型、房间数量、入住日期、费用口径，以及与每日路线的关系；区分候选和用户已选酒店。
9. **天气与携带建议**：针对出行日期的天气信息、衣物及必需品建议，说明天气信息是否覆盖整个行程。

用户应能理解推荐理由，例如“把附近的活动安排在同一天，减少往返”。时间和费用采用符合数据精度的估算，避免没有依据的分钟级或金额级精确值。

### 5.2 规划规则

- 优先按地理区域组织活动，减少不必要的折返。
- 计入活动间交通、用餐、休息和合理机动时间。
- 根据用户节奏控制活动数量，不默认填满所有空闲时间。
- 首末日按实际可用时间安排，不默认都是完整游玩日。
- 检查已知的开放时间、固定预约、交通衔接和预算约束。
- 明确必去项目与普通推荐的优先级；安排不下时说明取舍。
- 无法满足所有要求时，指出冲突、受影响的安排及具体替代选择，等待用户决定后执行；不能静默放弃约束或超出预算。
- 酒店候选与行程联合考虑：检查住宿费用、房型适配、到达交通和每日出行便利性，用户选定酒店后重新检查路线。
- 日期变化时重新检查交通、酒店和景点信息，并将原日期的天气结果标记为不适用；用户点击打开当前行程时查询新日期的天气，不直接沿用原日期的结果。
- 用户确认交通与酒店候选后，将两者纳入同一行程规划，使用抵离时间和酒店位置重新检查首末日、每日路线和费用。仅选定其中一项时保存选择，另一项仍标为待选择，不自动补选。
- 用户指定酒店时，保留该酒店作为住宿安排并通过 MCP 核实必要信息。是否已预订、入住日期和房型等按实际需要澄清；不能把“想住该酒店”当作“已预订”。查询失败时保留用户陈述，说明无法核实的部分。
- 酒店费用单独计算时，不占用用户确认的旅行预算额度；仍单列住宿费用及其核实状态。计入预算时按入住晚数、房间数量和预算口径核算，避免将共享房间的总价重复算到每个人名下。

### 5.3 事实与估算

交通通过第三方 API/MCP 查询，酒店、景点和天气通过 MCP 查询。地点是否存在、营业时间、预约要求、交通时长和价格等信息，应来自可追溯的数据或标记为待核实。重要信息保留来源、适用日期和查询时间；估算值明确标为估算。查询到候选不代表已经订票、订房或完成预约。

用户陈述、外部查询结果和规划假设分别保存。查询失败、没有结果或服务不支持所需查询时，应主动向用户说明具体缺口及其对行程的影响。可以保留已核实部分或提供可核实的替代方案；核心条件或关键可行性无法确认时，暂停相关安排的确定，不把不完整方案呈现为已验证计划。

日期已确认不代表天气预报一定可用。若出行日期超出服务的预报范围，应说明暂时无法获取对应日期预报；季节性携带建议需标明依据，不得当作实际天气预报。已有行程的天气更新由用户点击打开当前行程触发，结果在页面内展示。

## 6. 行程动态调整

### 6.1 支持的调整

| 类型 | 示例 | 预期行为 |
| --- | --- | --- |
| 偏好与节奏 | “太赶了”“多安排美食”“减少步行” | 调整活动密度、内容和移动方式 |
| 增删替换 | “不去这个景点”“加一个博物馆” | 检查时间、地理位置及费用后修改 |
| 移动时段 | “这个放到明天上午” | 检查目标时段以及原时段的衔接 |
| 时间变化 | “晚到了两小时”“提前一天回去” | 更新可用时间，重排受影响内容 |
| 现场变化 | “下雨了”“景点关闭了”“走不动了” | 根据情况调整剩余活动和交通 |
| 执行进度 | “这里已经去过了”“这个跳过了” | 更新进度，避免重复安排 |
| 恢复版本 | “还是用上一个方案” | 恢复历史安排，保留最新实际完成情况 |

### 6.2 调整流程

1. 识别修改意图和范围：一个活动、某一天或整个行程。
2. 读取当前需求、最新行程、固定安排和执行进度。
3. 补充本次修改必需的上下文；“现在来不及了”可能需要当前位置和当前时间。
4. 查询必要的外部信息，生成修改方案，并检查受影响的时间、路线、酒店、天气、预约和预算。
5. 发现冲突时，向用户说明并提供选项；等待用户确定解决方案，再执行。用户的修改指令已经明确解决某项冲突时，无需重复确认同一决定。
6. 保存新版本，展示修改原因、变化内容和未解决问题。

优先局部修改。若必须影响其他天，向用户说明原因。不存在冲突的普通行程编辑可以直接生成新版本；存在冲突时按用户确认的方案执行。若用户提出的解决方案仍无法执行，例如活动已闭馆或交通无法衔接，应说明剩余冲突并继续协商。

### 6.3 约束与实际状态

**必须满足的约束**包括明确的出发截止时间、已预约时段、用户要求保留的项目、预算上限和行动限制。

**可协商的偏好**包括推荐项目、活动顺序、希望少走路和一般用餐安排。偏好可以通过对话提升为必须满足的约束，例如“每天步行不能超过 5 公里”。

已完成活动作为事实保留；已跳过活动未经用户要求不重新加入；正在进行的活动根据用户意图处理。修改规划不代表已变更真实订单或预约，界面需列出用户仍要自行处理的事项。

## 7. 会话、计划与执行状态

产品需要保存三类状态：

- **旅行需求**：已知信息、未知信息、假设、偏好、明确约束和信息来源，包含确认日期、人数、预算金额及口径、费用覆盖范围、酒店与房型需求。
- **行程计划**：每日活动、起终点、时间段、地点、交通、费用、优先级和核实状态。
- **执行情况**：未开始、进行中、已完成、已跳过，以及用户最近报告的位置和时间。

每次修改形成一个版本，记录变更内容和原因。计划版本与执行情况分别保存，恢复旧计划时不得把已经完成的活动恢复为未开始。

待解决冲突及用户确认的处理方案也需保存，避免后续修改重复询问或覆盖用户决定。外部查询结果保留来源、查询时间及适用日期，用于判断是否需要刷新。

交通和酒店保存候选、用户选定和用户报告已预订等不同状态。保存酒店费用是否计入预算，以及尚待回答的选项问题。用户点击选项与自然语言反馈都应更新对应需求和行程状态。

首版使用用户主动报告的位置和进度。设备当前时间可以辅助理解“现在”，但无法证明用户当前位置；规划未来日期或跨时区场景时，需要明确行程日期和当地时间。

## 8. 交互形式

“行程区”是展示旅行计划的页面区域，包括每日活动、交通、酒店、天气、预算和修改结果。电脑端采用聊天旁的面板，两侧展示同一旅行会话的最新状态。

用户通过聊天提出修改，例如“第二天少安排一点”，由智能体检查约束并更新行程。首版的活动增删、替换和移动统一通过自然语言完成。候选选择及是非确认仍通过前端选项反馈。

对话与行程展示联动：对话负责表达需求、追问和解释，行程展示负责查看每日安排和修改结果。

- 澄清阶段：展示已知需求与当前问题，支持快捷选项和自由输入。
- 生成阶段：保留当前需求；耗时操作展示真实进度，失败后可继续。
- 查看阶段：先展示每日概览，再展开活动明细、交通和费用。
- 修改阶段：突出变化的活动，说明是否影响其他日期或固定安排。
- 出行阶段：优先展示今天剩余安排，方便报告迟到、完成、跳过或疲惫。

移动端需要支持完整核心流程。用户也通过聊天报告活动完成、跳过或临时变化，智能体同步更新执行状态。

### 8.1 手机端展示

手机端采用“聊天／行程”两个可切换视图，一次占用完整屏幕，避免左右分栏导致内容过窄。

- 默认进入聊天，便于补齐需求；生成行程后展示“查看行程”的入口。
- 行程视图按日期展示活动卡片，可查看交通、酒店、天气与预算；旅途中优先展示今天。
- 用户在行程中点击“和智能体讨论这一天”等入口，可返回聊天并携带日期上下文；具体修改仍由用户描述。
- 智能体修改后，在聊天中展示变更摘要，并提供返回对应日期的入口；行程视图同步更新。
- 两个视图切换时保留聊天内容、当前查看日期和滚动位置，不因切换重置会话。

### 8.2 已确认的选项交互

- **候选选择**：交通和酒店以可点击候选展示。交通展示班次、抵离时间、费用等可用信息；酒店展示位置、房型、费用及推荐理由。每项候选都应能够与查询结果对应。
- **共同纳入规划**：用户选定交通和酒店后，用明确的操作将已选内容加入行程并触发规划；按需要展示当前已选组合，避免用户不清楚正在使用哪个方案。
- **是非确认**：提供“是／否”或含义更明确的按钮，例如“酒店单独计算／酒店计入预算”。
- **冲突选择**：展示具体解决方案及影响，用户点击后按所选方案执行。用户仍可在聊天中提出其他方案。
- **反馈处理**：点击后展示已选内容，避免重复提交造成重复添加。行程变化导致旧选项过期时，不直接执行旧操作，应基于最新行程展示有效选项。
- **未知答案**：必要时提供“暂不确定”等选项，但不把该选择视为已补齐日期或预算等核心条件。

所有查询不可用情况应主动展示说明，用户不需要再追问查询是否成功。

### 8.3 天气查询与更新

初版生成时，按确认日期通过 MCP 查询天气。已有行程采用用户操作触发更新：用户点击打开当前行程时，后端查询对应目的地与日期的天气，更新页面中的天气信息、衣物和必需品建议。

电脑端触发点是用户选择打开该行程；手机端触发点是进入当前行程视图。查看已打开行程的不同日期、滚动页面、返回浏览器前台和聊天消息更新不额外触发天气查询。

页面显示查询进度与查询时间。天气查询不阻塞用户查看其他行程内容；同一行程已有查询进行中时合并重复点击，避免并发重复请求。查询失败时主动说明，可以保留并标明仍适用于当前日期的旧数据，不能当作最新结果；不同日期的旧数据不能继续展示为当前天气。

发现影响行程的天气变化时，在当前页面提醒并提供可点击的调整选项。天气信息更新不自动修改用户已确认的活动安排，用户反馈后再由智能体调整。

首版天气更新由上述用户操作触发，采用请求与响应展示结果；后台定时查询与关闭页面后的主动推送列为后续能力。

## 9. 示例对话

以下用于说明交互行为，不代表已经验证的武汉旅游建议。

**用户：**“我想去武汉玩几天。”  
**智能体：**“你准备玩几天，大概什么时候去？这次和谁一起？”

**用户：**“3 天，日期还没定，和朋友两个人，主要想吃东西，别太赶。”  
**智能体：**“需要先确定具体日期，才能查询交通、酒店和当地天气。你打算哪天去、哪天回？预算每人大概多少，是否包含住宿和往返交通？”

**用户：**“先给我看看吧，没有必去的。”  
**智能体行为：**说明日期和预算仍需确认，可以继续收集兴趣和住宿偏好，但暂不生成初版行程，也不自行指定日期或预算。

**用户：**“2026 年 10 月 16 日到 18 日，每人 2000 元，包含住宿和往返高铁，从长沙出发。我们想住一间双床房。”  
**智能体行为：**记录日期、预算口径与覆盖范围、出发地和房型需求；查询交通、酒店、景点与天气，前端展示交通与酒店候选。用户点击选定并加入行程后，结合抵离时间和酒店位置规划。天气预报若暂未覆盖出行日期，主动说明。

**另一种住宿输入：**“酒店不用推荐了，我要住某某酒店。”  
**智能体行为：**记录用户指定酒店；如果住宿预算口径未知，询问酒店是否单独计算，前端展示“单独计算”和“计入预算”选项。根据点击反馈更新费用范围，并围绕指定酒店规划。

**用户：**“第二天还是有点赶。”  
**智能体行为：**减少第二天安排和步行负担，说明移除或移动了哪些活动；若移动到第三天，重新检查第三天的时间。

**用户：**“我现在才到酒店，已经下午 3 点了。”  
**智能体行为：**若酒店位置未知，先询问区域；根据当前时间和位置重排今天剩余活动，保留已完成项目并检查固定预约。

## 10. 首版验收标准

| 场景 | 通过标准 |
| --- | --- |
| 输入“武汉玩几天” | 不擅自确定天数；提出少量关键问题 |
| 一次提供多项信息 | 正确提取，不重复询问已经明确的信息 |
| 用户不知道日期 | 继续澄清或帮助选择日期；不假设日期，不生成初版行程 |
| 预算缺失 | 询问金额和覆盖范围，不擅自设置预算 |
| 预算未指定口径 | 默认人均，在需求摘要中展示 |
| 用户指定全体预算 | 按全体金额计算，并结合人数正确核算 |
| 用户说“先给我看看” | 核心条件齐全才生成草案；日期和预算缺失时继续澄清 |
| 天数或日期冲突 | 指出冲突并澄清，不静默选取其中一个 |
| 正常生成行程 | 包含每日路线、交通、休息、费用口径和待办事项 |
| 推荐酒店 | 通过 MCP 获取信息，符合日期、人数、房型、预算与偏好，并说明与路线的关系 |
| 用户选择交通与酒店 | 前端提供可点击候选；选择并加入后，两者共同成为行程规划依据 |
| 用户只选了一项 | 保存已选项，不自动确定另一项，不重复添加 |
| 用户指定酒店且预算口径未知 | 提供是否单独计算的选项，按反馈更新预算范围并使用指定酒店规划 |
| 酒店费用单独计算 | 不占用旅行预算额度，单列住宿费用；未知费用不当作零元 |
| 用户已说明住宿预算口径 | 直接采用，不重复确认 |
| 是非确认或冲突选择 | 前端提供明确选项，点击反馈与自然语言反馈均能正确更新状态 |
| 点击过期选项 | 不执行与最新行程不兼容的旧操作，展示当前有效选择 |
| 查询交通和景点 | 使用指定 API/MCP 数据，保留查询时间和适用日期，不虚构未返回信息 |
| 天气预报可用 | 通过 MCP 按确认日期提供天气及衣物、必需品建议 |
| 日期超出预报范围 | 主动说明不可查询，不把季节建议当作具体预报 |
| 用户说“太赶了” | 实际减少活动或移动负担，并展示变化 |
| 用户到达较晚 | 按剩余时间规划，不简单顺延导致闭馆或预约冲突 |
| 规划或修改存在冲突 | 展示冲突，取得用户决定后按其方案执行 |
| 修改涉及固定预约 | 保留约束；用户明确同意变更后更新计划，列出需自行处理的预约事项 |
| 用户标记活动完成 | 后续调整不重复安排该活动 |
| 用户恢复旧版本 | 恢复计划内容，保留最新执行事实 |
| 事实查询失败 | 主动说明缺失信息及影响，不编造地点、价格或查询结果 |
| 用户修改日期 | 刷新受影响的交通、酒店和景点信息；旧天气标记为不适用，点击打开行程时查询新日期天气 |
| 电脑端查看行程 | 聊天旁展示行程面板，修改后同步呈现最新安排 |
| 手机端查看行程 | “聊天／行程”全屏切换，保留会话和当前查看位置 |
| 用户点击打开当前行程 | 触发天气 MCP 查询，更新天气与携带建议，并展示查询时间 |
| 行程内部浏览或浏览器返回前台 | 不额外触发天气查询 |
| 天气查询期间重复点击 | 合并进行中的请求，其他行程内容仍可查看 |
| 天气变化影响户外安排 | 提醒并提供调整选项，收到用户反馈后再修改安排 |
| 用户修改活动安排 | 通过自然语言表达修改，智能体执行约束检查并更新行程 |
| 退出后继续 | 能恢复需求、最新行程和执行状态 |

## 11. 评估方式

首版使用代表性对话场景验证行为，再结合真实用户反馈评估：

- 达到可生成状态所需的追问轮数及用户中途退出情况。
- 重复追问、错误假设和需求遗漏情况。
- 行程中已知时间、路线和固定安排的冲突数量。
- 用户要求修改后，约束被保留的比例和无关内容被改动的情况。
- 关键事实有来源或明确核实状态的覆盖情况。
- 用户能否理解并执行方案，能否顺利继续修改。

具体数值目标在确定测试集和数据能力后补充。首版重点验证需求理解、行程可执行性和调整正确性。

## 12. 已确认范围与后续细化

本轮已确认手机端展示和天气更新策略。后续技术方案需细化各 API/MCP 的查询参数、返回字段、服务能力与天气预报覆盖范围；后续界面设计需细化候选卡片、行程面板和手机端视图布局。

已确定：首版为国内单城市自由行；交通信息通过第三方 API/MCP 获取，酒店、景点与天气信息通过 MCP 获取；预算为核心条件且默认人均；日期必须确认且不可假设；候选和确认问题通过前端选项反馈；选定交通与酒店后共同纳入规划；用户指定酒店时确认费用是否单独计算；冲突按用户确认的方案解决；查询不可用主动说明；电脑端采用聊天旁的行程面板；手机端采用“聊天／行程”全屏切换；用户通过自然语言让智能体修改安排；已有行程的天气在用户点击打开当前行程时更新。

后续技术方案应围绕这些产品行为确定数据结构、模型调用、工具查询和校验方式。
